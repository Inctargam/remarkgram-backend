# Lifecycle подписок и события Business-доступа

Реализована сторона D2: cron, атомарная запись событий и доставка в RabbitMQ.
User Accounts пока не принимает эти события и не переключает тип аккаунта.
Контракты D1 и ручной DBOS workflow не меняются.

## Обновление статусов

`SubscriptionStatusesScheduler` запускается раз в минуту с `waitForCompletion: true`.
Пользователи выбираются пакетами по 100 с курсором по `userId`. Для каждого открывается
отдельная Prisma-транзакция и берётся существующий `lockByUserId`.

После блокировки подписки перечитываются. Сначала истёкшие ACTIVE/PENDING становятся EXPIRED,
затем PENDING с `startsAt <= now < expiresAt` становятся ACTIVE. Время фиксируется после
ожидания блокировки. Даты, provider-связи и настройки автопродления не меняются.

После фактических изменений записывается один снимок итогового доступа. При переходе
A → B промежуточного события отключения нет. Повтор без изменений ничего не записывает.
Ошибка откатывает транзакцию пользователя; остальные обрабатываются дальше. Следующий
проход снова подберёт пользователя, которому всё ещё нужно обновить статус.

## Контракт события

Событие `subscriptions.business-access-changed.v1` использует общий `IntegrationEvent`:

```ts
{
  eventId: string,
  eventType: 'subscriptions.business-access-changed.v1',
  aggregateType: 'user',
  aggregateId: string,
  data: { userId: number, hasBusinessAccess: boolean, version: string }
}
```

`hasBusinessAccess` означает наличие ACTIVE/PENDING с текущим оплаченным периодом.
Снимок записывается после первого применения платежа и изменения lifecycle-статусов.
Replay платежа возвращает прежний результат без нового события.

`version` — положительное целое из `business_access_event_version_seq`, записанное десятичной
строкой для сохранения точности JSON. Версия выделяется под блокировкой пользователя;
пропуски после rollback допустимы. Consumer должен сравнивать версии как целые числа,
а не строки, и атомарно применять только `version > lastVersion` вместе с сохранением версии.
Это защищает и от повторов, и от поздней доставки старого состояния.

## Outbox и RabbitMQ

`@nestjs/outbox` использует `PostgresOutboxStore` и `fromPrisma`. Запись через `outbox.add(tx, …)`
входит в ту же транзакцию, что изменение подписок. До commit событие недоступно relay.

Ключ порядка публикации: `business-access:${userId}`. RabbitMQ-клиент объявляет durable-очередь
`user_accounts_business_access_queue` и отправляет persistent-сообщения с подтверждением брокера.
Пакет Nest `{ pattern, data }` содержит имя события в `pattern` и IntegrationEvent в `data`.
Очередь сохраняет события до появления consumer; подтверждение брокера ещё не означает
применение события в User Accounts.

Relay опрашивает outbox каждую секунду. При ошибке публикации — до 10 попыток с удвоением
задержки от 1 секунды до 60 секунд. Исчерпанные попытки сохраняются в dead letters пакета.
Повторная доставка возможна; идентификатор и версия события сохраняются.

## Подготовка запуска

1. Установить зависимости проекта.
2. Задать `DATABASE_URL` для Payments и `AMQPS_URL` для RabbitMQ по существующей схеме конфигурации.
3. Перед запуском применить подготовленные миграции Payments штатной командой
   `pnpm prisma:payments:migrate:deploy` в нужном окружении.
4. Запустить Payments. Воркер и relay запускаются вместе с приложением.

В этой задаче миграции **не запускались**. Новая миграция содержит служебную схему `nest_outbox`
и sequence версий. Store настроен с `migrate: false`: без подготовленной схемы запуск завершится
ошибкой, а не перейдёт на хранение в памяти. Собственных Prisma-моделей outbox нет.

Проверки написаны, но тесты, TypeScript, ESLint и форматтеры не запускались. Интеграционные
сценарии требуют отдельную БД с применёнными миграциями через `PAYMENTS_INTEGRATION_DATABASE_URL`.
