## Следующая итерация: нетерминальный FAILED (2026-10-28)

Статус: согласовано направление доработки; реализация отложена на следующую итерацию.
Текущие диаграммы описывают существующее поведение, а не целевую семантику ниже.

### Историческая ошибка определения

В [контексте Payments](../agent-context.md#payment-status) `PaymentStatus.FAILED` исторически
определён как terminal failure (окончательная финансовая неудача). Это определение закреплено
в domain state machine, application handlers и условиях обновления репозитория. При этом ни один
поддерживаемый handler не устанавливает FAILED: `payment_intent.payment_failed` и
`invoice.payment_failed` обрабатываются для correlation/audit без изменения статуса Payment.

Для согласованной модели такая терминальность ошибочна: FAILED должен отражать подтверждённую
провайдером неудачную попытку оплаты, после которой ещё возможны успешная оплата или окончательная
отмена. Исторический запрет перехода FAILED → SUCCEEDED препятствует этой семантике.
Прежние описания терминального FAILED сохраняются как описание текущей реализации до выполнения
этой итерации; их нельзя использовать как целевое бизнес-правило.

### Целевая семантика и инварианты

FAILED — нетерминальная financial projection (локальная проекция финансовых событий провайдера):
для данного Payment зафиксирована неудачная попытка оплаты, но успешная оплата и окончательная
отмена ещё не подтверждены. Статус не заменяет audit trail (историю событий для расследования).

| Текущее состояние | Согласованный failure event | Подтверждённый success | Подтверждённая cancellation |
| --- | --- | --- | --- |
| CREATED / PENDING | FAILED | SUCCEEDED | CANCELED |
| FAILED | FAILED | SUCCEEDED | CANCELED |
| SUCCEEDED | Сохранить статус, записать аудит | Идемпотентный результат | Сохранить статус |
| CANCELED | Сохранить статус, записать аудит | Сохранить статус, зафиксировать противоречие для reconciliation | Идемпотентный результат |

Каждый переход требует reconciliation (сверки принадлежности события конкретному Payment и
совместимости provider references). Для invoice-backed оплаты необходимо отличать исходную
покупку из metadata от конкретного renewal, определяемого по Invoice.

- `payment_intent.payment_failed` и `invoice.payment_failed` становятся основаниями для FAILED
  после соответствующей сверки. Ошибки workflow, БД, timeout и исчерпание application retry
  финансовый FAILED не устанавливают.
- SUCCEEDED и CANCELED остаются терминальными; failure event не изменяет эти статусы.
  Защита реализуется conditional update (атомарным обновлением с условием текущего статуса),
  чтобы конкурентный failure не перезаписал success/cancellation.
- `SUCCEEDED` по-прежнему требует `paidAt != null`. Failure не устанавливает дату успешной оплаты.
- Поздние failure events сохраняются для аудита независимо от изменения проекции Payment.
  Повторная доставка должна обрабатываться идемпотентно.
- Запуск повторного списания сам по себе не переводит FAILED обратно в PENDING.
- FAILED продолжает участвовать в concurrency policy незавершённой покупки. Повторная оплата
  не должна автоматически создавать новый Checkout; доступность существующего Checkout требует
  отдельной проверки его состояния и срока действия.
- Семантика `invoice.marked_uncollectible` остаётся отдельным решением; данная итерация не
  приравнивает признание долга невзыскиваемым к неудачной попытке списания.

### Объём и сложность изменения

Это изменение бизнес-поведения, а не behavior-preserving refactoring (рефакторинг с сохранением
наблюдаемого поведения). Подготовительные структурные изменения могут сохранять поведение,
но новые переходы FAILED и запись статуса по failure events намеренно меняют бизнес-правила.
Остальные действующие политики сохраняются: терминальность SUCCEEDED/CANCELED, reconciliation,
идемпотентность, обязательный paidAt для success и отсутствие начисления доступа по failure.

Предварительная оценка: **средняя сложность, 2–3 рабочих дня**, включая тесты и актуализацию
документации, без отдельной модели попыток. Это оценка по просмотренным участкам, а не срок
завершённой реализации.

В согласованный пакет изменений входят:

1. Domain state machine и централизованное определение терминальных состояний.
2. Failure handlers, application port и атомарная запись FAILED в persistence adapter.
3. Success/cancellation handlers и SQL-предикаты, допускающие исходное состояние FAILED.
4. Enrichment provider references, получение существующего Checkout и ограничения конкурирующих покупок.
5. Сценарии тестирования и синхронизация agent context, event specifications и диаграмм.

Основная сложность — распределённость прежнего правила терминальности по слоям. Основные риски:
race condition (конкурентная обработка success/failure), доставка событий вне порядка, неверная
корреляция renewal и нарушение защиты от конкурирующей покупки.

Для завершения итерации рекомендуются unit tests переходов и handlers, integration tests
условных обновлений и проверка типов payments. Ключевые сценарии: failure → success,
failure → cancellation, повторные и запоздавшие failure events, конкурентные success/failure,
failure до enrichment и сохранение concurrency policy. Запуск проверок — по явному запросу
пользователя; при добавлении этой записи tests/build/lint/formatter не запускались.

### Последующее расширение аудита

Отдельная модель PaymentAttempt и счётчик неудачных списаний не входят в эту итерацию.
Предварительная дополнительная оценка — **2–4 рабочих дня**, с уточнением после определения
идентичности попытки и правил correlation.

Количество webhook events нельзя считать количеством попыток: возможны повторные доставки
и разные события PaymentIntent/Invoice об одном списании. Нужны дедупликация событий и
сопоставление уникальным попыткам. Будущий failedAttemptsCount целесообразно определять как
derived value (значение по истории уникальных неудачных попыток), а не увеличивать на каждый webhook.
Stripe attempt_count также нельзя напрямую приравнивать числу фактических неудачных списаний:
он может увеличиваться при запланированных, но не выполненных retry.
См. [Stripe: webhook ordering и duplicates](https://docs.stripe.com/webhooks) и
[Stripe: retry attempt_count](https://docs.stripe.com/billing/revenue-recovery/smart-retries).
