# Карточки методов D2 для работы с подписками

Четыре метода D2, которые вызывает D1. Реализация адаптирована к обновлённым контрактам
28 октября 2026 года; ниже — требования к их поведению.

**Общие правила.** D1 проверяет оплату и вызывает Stripe. D2 работает с локальными
подписками. В методах с `tx` все записи идут через переданную транзакцию: её завершает
вызывающий код. Ошибка откатывает этот шаг. Повтор вызова не должен повторно начислять
доступ или менять уже подтверждённую привязку.

Подписка приложения и подписка Stripe — разные объекты. Ниже `A` и `B` обозначают
локальные UUID, а `sub_old` и `sub_new` — идентификаторы Stripe.

**1. Проверить наличие активной подписки — `hasActiveSubscription`**

**Когда:** перед созданием платежа. D1 нужно узнать, есть ли сейчас активная подписка.

```ts
hasActiveSubscription(userId: number): Promise<boolean>;
```

**Сделать:** найти текущий оплаченный период указанного пользователя и вернуть признак её наличия.
Ничего не создавать, не резервировать и не менять статусы.

**Результаты:**

- Найдена A → `true`.
- Нет активной подписки → `false`.
- Ошибка БД → выбросить ошибку. Несколько активных подписок → ошибка нарушения правил,
  а не выбор первой строки.

**Повтор:** обычное повторное чтение. Результат может измениться, если изменились подписки.

**Правило текущей реализации:** `startsAt <= now < expiresAt` и статус `ACTIVE` или
`PENDING`. Так уже начавшийся оплаченный период учитывается, даже если фоновая задача
ещё не переключила `PENDING` в `ACTIVE`. Истёкшая по датам подписка не учитывается,
даже если её статус ещё `ACTIVE`. Статус `EXPIRED` исключён. Две подходящие записи — ошибка.

**2. Применить оплату — `applySuccessfulPayment`**

**Когда:** D1 уже сохранил подтверждённую оплату. Этот метод предоставляет оплаченный доступ.

```ts
applySuccessfulPayment(
  payment: SuccessfulPayment,
  tx: PaymentsTransactionContext,
): Promise<ApplySuccessfulPaymentResult>;
```

**Что приходит:** `paymentId`, `userId`, `planId`, тип `PURCHASE` или `RENEWAL`,
длительность `periodCount/periodUnit`, время оплаты `paidAt`,
намерение `autoRenewalRequested`, сумма, валюта,
провайдер, `providerSubscriptionId` и `providerCustomerId`. Даты передаются UTC ISO-строками.
Цель PURCHASE определяется по очереди пользователя,
RENEWAL — по provider-связи. `targetSubscriptionId` удалён из контракта и не передаётся.

**Сделать:** сначала найти сохранённый результат по `paymentId`. Если его нет,
проверить владельца и состояние, применить оплаченный период и сохранить результат
в той же транзакции. Периоды не должны пересекаться, включая конкурентные покупки.

Примеры для месячного тарифа, своевременной обработки и отсутствия других покупок:

| Сценарий | Изменение D2 | Результат |
| --- | --- | --- |
| Первая покупка 1 ноября, доступа нет | Создать A на 1 ноября — 1 декабря | `CREATED`, ID A |
| 15 ноября куплен ещё месяц, A действует до 1 декабря | Создать B на 1 декабря — 1 января; A продолжает действовать | `SCHEDULED`, ID B |
| Подтверждено автосписание 1 января за B | Продлить B до 1 февраля | `RENEWED`, ID B |

**Вернуть:**

```ts
type ApplySuccessfulPaymentResult = {
  subscriptionId: string;
  action: 'CREATED' | 'SCHEDULED' | 'RENEWED';
  nextSubscriptionStartsAt: string;
  previousProviderSubscriptionId: string | null;
};
```

Для дополнительной покупки из примера дата равна `2027-01-01T00:00:00.000Z`,
а прежний provider ID — `sub_old`. Дата означает конец всей оплаченной цепочки,
включая новую покупку. Для `CREATED/RENEWED` прежний ID равен `null`; валидная
UTC ISO-строка даты тоже обязательна, хотя D1 не использует её для нового списания.

**Повтор:** вернуть весь первоначальный результат, не пересчитывая дату по текущей
подписке и не продлевая доступ снова. Конфликт владельца или состояния — ошибка;
нельзя молча выбрать произвольную подписку. D1 сам запишет `Payment.subscriptionId`.

**Реализована первая покупка:** `PURCHASE` при отсутствии текущих/будущих периодов,
незавершённых изменений и прежнего включённого автопродления. Период начинается в `paidAt`;
месяцы календарные с ограничением последним днём месяца. Исторические периоды не должны
пересекаться с новым. Запоздавшая оплата сохраняет исходные даты; истёкший период получает EXPIRED.
Подписка и результат CREATED записываются в переданный `tx`, повтор возвращает тот же результат.
Для первой provider-привязки добавлен `providerSubscriptionId?: string | null`: D1 передаёт
сохранённый ID из Payment. При запрошенном автопродлении без него D2 возвращает ошибку.

**Дополнительная покупка реализована:** выбрать конец оплаченной очереди (включая PENDING),
создать новую строку от `max(paidAt, expiresAt последней подписки)` и вернуть SCHEDULED.
Старая связь получает DISABLING, новая — ENABLING. В той же транзакции сохраняются
SubscriptionPaymentApplication и AutoRenewalOperation типа TRANSFER со статусом PENDING.
ID операции равен paymentId; sourceSubscriptionId и sourceProviderSubscriptionId сохраняют старую связь.
CREATED и RENEWED создают только применение платежа, без операции автопродления.
Публичный previousProviderSubscriptionId при повторе берётся из неизменяемого снимка операции.
Истёкшая подписка с ENABLED тоже требует отключения прежнего recurring billing.

**RENEWAL реализован:** найти подписку этого пользователя по паре provider + providerSubscriptionId,
проверить совпадение плана, добавить оплаченный период к её `expiresAt`, вернуть RENEWED.
`paidAt` не сдвигает начало продления при задержке webhook. Новая строка Subscription не создаётся,
настройка автопродления не меняется: подтверждённое списание могло предшествовать её отключению.
Пересечение с другим оплаченным периодом — конфликт, очередь автоматически не сдвигается.

**Ограничения текущего контракта:** SCHEDULED требует прежнюю незавершённую provider-связь,
того же провайдера и `autoRenewalRequested=true`, поскольку D1 всегда выполняет оба provider-шага.
Другие сочетания отклоняются до сохранения новой подписки. Нужен отдельный контракт для покупки
после одноразовой подписки без provider ID или без нового автопродления.
RENEWAL начисляется последовательно от локального конца периода: контракт не содержит границ
расчётного периода Invoice, поэтому точная сверка с ними и разрешение позднего конфликта с очередью
требуют отдельного решения. События Business-доступа ещё не реализованы.

**3. Зафиксировать отключение старого продления — `confirmAutoRenewalCancellation`**

**Когда:** после SCHEDULED и подтверждения Stripe, что старое автопродление отключено.

```ts
confirmAutoRenewalCancellation(
  paymentId: string,
  providerSubscriptionId: string,
  tx: PaymentsTransactionContext,
): Promise<void>;
```

**Что приходит:** paymentId дополнительной покупки и старый `sub_old`.

**Сделать:** прочитать применение по paymentId, взять lock пользователя и перечитать применение
вместе с операцией. Проверить SCHEDULED, наличие TRANSFER, старой локальной связи
и совпадение sub_old с sourceProviderSubscriptionId. Отсутствие или несовпадение — конфликт.
При PENDING одной nested-записью установить A = RETIRED, операции — BINDING_PENDING.
A определяется через sourceSubscriptionId; даты A и B не менять.

**Повтор:** BINDING_PENDING или COMPLETED → успех без записи после проверки входящих ID.
Текущее состояние B не читаем: оно могло измениться после завершения операции.
Конфликты — SubscriptionCancellationConflictError; ошибки БД передаются D1 для отката tx.

**4. Сохранить новую provider-привязку — `bindProviderSubscription`**

**Когда:** D1 создал новую подписку Stripe после подтверждённого отключения старого продления.

```ts
bindProviderSubscription(
  paymentId: string,
  providerSubscriptionId: string,
  tx: PaymentsTransactionContext,
): Promise<void>;
```

**Что приходит:** paymentId дополнительной покупки и новый `sub_new`.

**Сделать:** получить владельца применения платежа, взять lock и перечитать применение вместе с операцией.
Проверить SCHEDULED и наличие TRANSFER. B определяется из сохранённой операции.
При BINDING_PENDING одной nested-записью сохранить B.providerSubscriptionId
и ENABLED, операции — COMPLETED и снимок providerSubscriptionId. Даты доступа сохранить.
PENDING → ошибка: отключение ещё не подтверждено.

**Повтор:** при COMPLETED тот же provider ID в снимке операции → успех без изменений;
другой ID → SubscriptionBindingConflictError. Текущие состояния A и B не проверяем.
Ручное отключение автопродления после привязки не будет отменено поздним повтором.
Конфликт уникальности provider-привязки тоже возвращается как SubscriptionBindingConflictError.

**Общие гарантии:** связи и владельцы проверяются при создании операции и неизменяемы.
Состояния ENABLING/DISABLING блокируют конкурирующие изменения; ручные операции
соблюдают их и общий lock. RETIRED запрещает повторное включение старой связи.
D1 гарантирует непустой новый provider ID и управляет commit/rollback общего tx.
Эти методы не начисляют периоды и не вызывают Stripe.

В Subscription нет autoRenewalChangeId. Ручной workflow один раз устойчиво
создаёт AutoRenewalOperation.id и передаёт его D1 как autoRenewalChangeId. Клиентский ключ
в таблице не хранится; дедупликация запуска остаётся на уровне workflow.

Expiration и события Business-доступа остаются отдельными задачами D2.
Ручное переключение реализовано следующими командами, пока без HTTP/gRPC API.

Точные объявления: [порт чтения](../../apps/payments/src/features/payments/application/ports/subscription-context.port.ts),
[обработчик платежа](../../apps/payments/src/features/payments/application/ports/subscription-payment.handler.ts),

**5–6. Ручное включение и выключение автопродления**

Команды: EnableSubscriptionAutoRenewalCommand и DisableSubscriptionAutoRenewalCommand.
Обе принимают `{ userId, subscriptionId, idempotencyKey }` через CommandBus.
Результат: `{ operationId, subscriptionId, autoRenewalEnabled }`.

**Когда:** пользователь меняет настройку последней подписки, включая будущую после binding.
Включение — только до expiresAt; отключение допускается и после истечения доступа.
Чужая подписка, отсутствие provider ID, RETIRED или незавершённое переключение — конфликт.

**Процесс:** DBOS создаёт UUID → подготовка под lock → D1 вне транзакции → подтверждение под lock.
Подготовка пишет ENABLE/DISABLE, снимок provider ID, PENDING и ENABLING/DISABLING.
Подтверждение пишет COMPLETED и ENABLED/DISABLED. Даты не меняются. Если нужное состояние
уже установлено, операция сразу COMPLETED, вызова D1 нет.

**Повтор:** тот же клиентский ключ и аргументы возвращают прежний результат workflow; другое
действие или subscriptionId с тем же ключом — конфликт. Новый ключ означает новое изменение.
Поздний повтор старой операции не отменяет последующее действие; результат относится к операции.

**Сбой:** внешний step делает до 10 попыток только для provider unavailable/outcome unknown.
Локальные транзакции вызываются напрямую, без ручного retry-loop; встроенные повторы конфликтов
datasource сохраняются. Необработанный локальный сбой завершает workflow с ERROR. Если подготовка
уже зафиксирована, операция сохраняет переходное состояние и блокировку. Повтор ключа возвращает
прежнюю ошибку. Автоматическое восстановление ERROR пока не реализовано.
Клиентский ключ в таблице не хранится.

Подробности: [ручное автопродление](./auto-renewal-d1-d2-contract.md).
