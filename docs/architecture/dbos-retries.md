# Повторы вызовов Files в DBOS

CreatePost и SetAvatar используют встроенные ретраи `@DBOS.step`:
`retriesAllowed: true`, `maxAttempts: 3`, `intervalSeconds: 1`, `backoffRate: 2`.
Всего три попытки: первая выполняется сразу, следующие — после пауз 1 и 2 секунды.

| Workflow   | Шаги с повторами                                                    |
| ---------- | ------------------------------------------------------------------- |
| CreatePost | `reserveImages`, `attachImages`, `releaseReservation` (компенсация) |
| SetAvatar  | `attachAvatar`                                                      |

`shouldRetry` разрешает только локальные ошибки недоступности Files, в которые gRPC-адаптеры
преобразуют `UNAVAILABLE` и `DEADLINE_EXCEEDED`. Валидация, конфликт состояния, отсутствие
файла и неизвестные ошибки завершают шаг без повторов. Параметры, `operationId` и
`reservationId` не меняются между попытками: потерянный ответ после commit Files
безопасно обрабатывается существующей идемпотентностью Files.

## После исчерпания попыток

DBOS сохраняет `DBOSMaxStepRetriesError` со списком причин. На границе workflow mapper
преобразует её в существующую ошибку недоступности Files, только если все причины
распознаны как временные. gRPC возвращает `UNAVAILABLE`, Gateway — HTTP `503`.
Исходная ошибка остаётся в истории, технический отказ логируется с `workflowId`.

Компенсация при неизвестном результате RPC не запускается. SetAvatar сохраняет блокировку
профиля. CreatePost сохраняет достигнутое состояние: например, неопубликованный пост
после сбоя прикрепления или незавершённой компенсации. Повтор с прежним ключом получает
сохранённую ошибку и не запускает новые попытки. Автоматический fork не добавлен;
окончательный технический отказ требует отдельного восстановления.

## Границы

3 секунды — сумма пауз одного шага, а не таймаут операции. gRPC-дедлайны, deadline propagation,
HTTP-таймер и повторы в адаптерах не добавлены. Зависший вызов сам по себе не запустит ретрай:
для повтора он должен завершиться распознанной временной ошибкой.
Общее ожидание складывается из времени самих вызовов и пауз; у CreatePost задержки
нескольких шагов могут суммироваться. При успехе с первой попытки дополнительных пауз нет.

Встроенные повторы конфликтов транзакций Prisma datasource не изменены. Общие повторы при
недоступности PostgreSQL этой настройкой не покрываются. Число попыток шага не следует
считать глобальным бюджетом через все падения процесса: при восстановлении незавершённый
шаг может выполняться снова. Повтор использует прежние параметры RPC и идентификатор операции.

Проверки с настоящим SDK и изолированной PostgreSQL находятся в интеграционных тестах
CreatePost и SetAvatar: потеря ответа, успешный повтор, повторы компенсации, исчерпание
попыток и повторное чтение ошибки из истории. Unit-тесты mapper дополнительно проверяют,
что ошибки с неизвестными или смешанными причинами не превращаются в `503`.
