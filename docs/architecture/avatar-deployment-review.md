## Повторная проверка удаления — 26 сентября 2026

Проверена актуальная цепочка: HTTP DELETE → транзакция Profile + AvatarDeletionRequest + OutboxEvent →
RabbitMQ → consumer Files → транзакция soft delete + FileDeletionJob → worker удаления.
Замена аватара и компенсация SetAvatar также сохраняют запрос удаления через outbox.

- 1079 unit-тестов, 70 HTTP-тестов Gateway с gRPC-заглушками и 58 интеграционных тестов прошли.
- Сборки Files, user-accounts и Gateway, lint исправленных файлов и git diff --check прошли.
- Интеграционные проверки выполнены на изолированных PostgreSQL 16 и RabbitMQ 4.3.5:
  применены миграции в пустые базы, проверены откаты, конкурентные DELETE/SET, старые ключи,
  SKIP LOCKED, потери подтверждения, quorum-повторы, DLQ и восстановление DBOS после SIGKILL.
- Топология объявляется из кода AMQP-пользователем без административных тегов; проверено
  восстановление bindings после переподключения. Импорт JSON и Management API приложениям не нужны.
- Исправлены старый комментарий о quorum policy и формулировка Swagger о способе хранения запроса.
- Старый внутренний RPC ScheduleAttachedFileDeletion сохранён: обычный поток user-accounts его
  не вызывает, но он указан как инструмент ручного восстановления в set-avatar.md.

Оставшиеся ограничения не изменены: техническая ошибка SetAvatar может завершить workflow в ERROR
с установленным avatarUpdateId; DELETE тогда возвращает 409 до согласованного восстановления.
Outbox повторяет неопубликованные события при старте и каждые 6 часов. FileDeletionJob обрабатывается
пачками до 100 задач за запуск, имеет до 5 попыток и статус DEAD после их исчерпания. Ошибки S3
не возвращаются в RabbitMQ, поскольку сообщение уже подтверждено после сохранения задачи.

Рабочие CloudAMQP, Neon и S3 не изменялись. Реальное удаление объекта в пользовательском S3
и полный браузерный сценарий требуют проверки после развёртывания.

Проверены загрузка и подтверждение, установка/замена, DELETE, чтение профиля/файла,
ошибки, outbox, quorum RabbitMQ, миграции, сборки и восстановление DBOS.
Поведение приложений в ходе проверки не изменялось.

## Что подтверждено

- Инициация одного JPEG/PNG размером 1–10485760 байт; ограничение размера в подписанной S3 policy.
- Подтверждение сверяет размер и Content-Type объекта с записью Files.
- SetAvatar повторно проверяет владельца, статус и метаданные: endpoint загрузки постов
  не позволяет обойти лимит аватара. Ошибка откатывает прикрепление в Files.
- Первичная установка создаёт профиль; замена сохраняет остальные поля. Старый файл
  ставится на удаление после переключения ссылки. При бизнес-отказе прежний аватар сохраняется.
- DELETE одной транзакцией очищает ссылку, записывает журнал ключа и outbox.
  Повтор старого ключа не удаляет новый аватар, активная замена даёт конфликт.
- Outbox и checkpoint DBOS фиксируются атомарно. Ошибка брокера не отменяет DELETE
  и не удерживает блокировку успешно установленного аватара.
- Конкуренция установки с DELETE, резервированием поста и очисткой файлов проверена на PostgreSQL.
- Восстановление DBOS проверено после SIGKILL на нескольких границах: прикрепление,
  смена ссылки, транзакция outbox и её commit.
- RabbitMQ выполняет первую попытку и три повтора с задержкой (в тесте 100 мс вместо минуты),
  постоянные ошибки и исчерпание лимита направляются в DLQ. Другие подписчики не получают повторов Files.
- После утраты результата публикации eventId сохраняется. Два consumer делят одну очередь.
- Перенос в DLQ восстанавливается после возврата удалённой привязки; для локального теста
  внутренний интервал повторной публикации брокера сокращён до 1 секунды.
- FileDeletionJob сохраняется до ack; физическое удаление остаётся за существующим worker.

## Ограничения, которые нужно учитывать

### 1. Ошибка связи с Files может оставить смену аватара заблокированной

[Workflow](../../apps/user-accounts/src/features/users/infrastructure/dbos/dbos-set-avatar.workflow.ts)
сохраняет avatarUpdateId при неизвестном результате RPC. Это защищает от несогласованности,
после 5 неудачных попыток шага ошибка записывается в DBOS как ERROR.
Повторы выполняет DBOS; дополнительных ретраев в gRPC-адаптерах нет.
Повтор того же ключа воспроизводит ошибку; новый SET или DELETE получает 409.
Обычный перезапуск автоматически восстанавливает PENDING после падения процесса, но не исправляет
уже записанную ошибку шага. Нужен ручной разбор по инструкции в [set-avatar.md](set-avatar.md).
Не снимать блокировку вслепую. Для учебного запуска это принятое ограничение;
для работы без ручного сопровождения нужен отдельно согласованный механизм восстановления.

Собственного HTTP-таймера ожидания и gRPC deadline тоже нет по ранее принятому решению.
Внешний ingress может оборвать ожидание раньше завершения workflow; клиент повторяет тот же ключ.

### 2. Текущая конфигурация DBOS рассчитана на один экземпляр user-accounts

[executorID](../../apps/user-accounts/src/config/dbos.config.ts) фиксирован:
`remarkgram-user-accounts-singleton`. При старте DBOS восстанавливает PENDING этого executor.
[Deployment](../../apps/user-accounts/deployment.yaml) не задаёт стратегию обновления:
стандартный RollingUpdate допускает одновременную работу старого и нового Pod.

Для текущего запуска завершить активные workflow, остановить старый экземпляр и только затем
запускать новый. Не масштабировать user-accounts без настройки отдельных executor ID и восстановления.
Переход на новую последовательность шагов нельзя выполнять поверх незавершённых старых workflow.
[DBOS executorID](https://docs.dbos.dev/typescript/reference/configuration),
[Workflow recovery](https://docs.dbos.dev/production/workflow-recovery),
[Kubernetes Deployment](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/).

### 3. Асинхронное удаление требует наблюдения за ошибками

Недоступность RabbitMQ оставляет outbox неопубликованным; резервная отправка может ждать до 6 часов.
Неисправимые события находятся в DLQ. Ошибки S3 обрабатываются FileDeletionJobsWorker:
после пяти попыток задача становится DEAD. Worker обрабатывает одну пачку до 100 задач за запуск,
резервное расписание — каждые 6 часов. При большом накоплении обработка может занять несколько запусков.
Это не препятствует исчезновению аватара из профиля: DELETE уже зафиксировал avatarFileId = null.

## Подготовка окружения и порядок запуска

1. Заполнить секреты платформы. У user-accounts нужны DATABASE*URL, FILES_GRPC_URL,
   USER_ACCOUNTS_DBOS_SYSTEM_DATABASE_URL и AMQPS_URL. У Files — DATABASE_URL, FILES_GRPC_URL,
   AMQPS_URL и FILES_S3*\*; Gateway должен обращаться к правильным адресам Files/user-accounts.
   DBOS system URL должен быть прямым либо session-pooled; нужны права создавать внутренние схемы.
   AMQPS_URL обоих сервисов должен указывать на один virtual host.
2. При повторной проверке 26 сентября необходимые DATABASE_URL и AMQPS_URL в локальных
   `.env.development.local` Files/user-accounts заполнены; FILES_GRPC_URL и
   USER_ACCOUNTS_DBOS_SYSTEM_DATABASE_URL у user-accounts также заполнены.
   Соответствующие ссылки в deployment присутствуют. Успешность подключений к этим адресам не проверялась.
   Значения секретов платформы не проверялись.
3. Применить миграции Files и user-accounts командами `pnpm prisma:files:migrate:deploy` и
   `pnpm prisma:user-accounts:migrate:deploy` с явно выбранным DATABASE_URL нужного сервиса.
   Команды миграций сами по себе не запускаются в Docker CMD, Prisma CLI и миграции не копируются
   в финальный runtime-образ: выполнить их из checkout/отдельного migration job до запуска.
4. Проверить RabbitMQ 4.3+ и права configure/write/read на объекты своего vhost.
   Топология теперь объявляется приложениями через AMQP, импорт definitions не нужен.
   Подробности — [инструкция RabbitMQ](avatar-rabbitmq.md).
5. Запустить Files, затем user-accounts, затем Gateway. Для обновления user-accounts соблюдать
   порядок остановки выше. Убедиться, что приложение стартовало, а у основной очереди появился consumer.
6. Проверить на платформе: JPEG/PNG → POST avatar-upload → загрузка в S3 → complete → PUT avatar →
   чтение профиля и изображения → замена → DELETE. Проверить повтор DELETE с прежним ключом после
   новой установки. Для прямой браузерной загрузки должны быть настроены CORS бакета и Gateway;
   учётные данные Files должны позволять необходимые операции S3, включая удаление.
